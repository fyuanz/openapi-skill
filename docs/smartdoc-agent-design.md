# SmartDoc-Agent 产品与架构设计

> 版本：3.6.0
>
> 日期：2026-09-14
>
> 状态：测试案例作为生成验收依据；新增可配置的微服务独立 Skill 与汇总 Skill；Skill 使用效果由用户人工校验
>
> 本版移除 web/前端及真实环境验收计划，支持独立、汇总、共存三种输出。历史技术决策保留在 `codex/DECISIONS.md`。

## 1. 产品目标

将接口文档生成一个供前端开发使用的 Skill。每次编译都触发更新；Skill 生成异常不得中断业务项目编译。其余事项暂不做。

当前只接收 SpringDoc 或基于 SpringDoc 的 NextDoc4j 产出的 OpenAPI 3.1.0 JSON，面向 Codex 项目 Skill。生成器只转换 JSON 中已有的接口事实，不调用 LLM 补造内容，不重新实现框架的接口扫描，也不解析文档 UI 页面。

“更新”表示每次编译都执行更新流程并使成功产物对应本次输入；相同接口文档可以产生相同内容，无须人为改变接口内容或发布版本。

### 1.1 微服务、多包与多文档是当前必需场景

默认以服务为生成和失败隔离单位，一个服务可以配置一份或多份 OpenAPI 文档。通过 `outputMode=service|aggregate|both` 选择仅生成单服务 Skill、仅生成唯一完整汇总 Skill，或两者共存。汇总范围由显式服务清单确定，服务和文档身份始终保留。

| 项目组织 | 处理方式 |
| --- | --- |
| 单服务、多个 Java 包、最终一份文档 | 作为单文档输入；包扫描范围由已有文档生产工具负责 |
| 单服务、多个文档分组 | 所有配置文档就绪后，生成该服务的一个完整 Skill |
| 单服务跨多个 Maven 模块 | 明确一个生成责任模块/编译入口及所需文档，验证文档就绪顺序 |
| 多个微服务，同仓库或不同仓库 | 各服务独立配置、编译和更新自己的 Skill，不依赖其他服务的 Skill 生成结果 |
| 多服务完整汇总 | 指定唯一协调入口及全部服务的本地文档源；所有必需服务就绪后生成一份独立完整 Skill |
| 汇总与单服务共存 | 协调入口配置 `both`，分别发布服务目录和汇总目录；或独立服务入口配合一个 `aggregate` 协调入口 |

Java 包、Maven 模块、文档分组与微服务不是一一对应关系，不通过目录名自动猜测服务边界。

## 2. 范围评审：哪些有必要做

| 能力 | 结论 | 原因与最小实现 |
| --- | --- | --- |
| OpenAPI 读取与必要校验 | 必做 | 读取接口事实；不支持或无效输入明确报错，交由编译集成层降级 |
| 服务归属、多文档输入和命名隔离 | 必做 | 服务独立更新；同一服务的文档分组共同组成完整 Skill，同名内容不会覆盖 |
| 接口、请求、响应、鉴权、Schema 提取 | 必做 | 前端必须知道怎么调用接口、传什么、返回什么 |
| `SKILL.md` 与按需读取的 references | 必做 | 让 Agent 找到接口资料，避免每次读取整份契约 |
| 紧凑目录、operation、共享 Schema 分片 | 必做 | 能从 method/path/名称找到接口并继续定位字段；tag 导航按文档需要生成 |
| 本地 `$ref`、共享和递归关系 | 必做 | 保留契约关联，不重复展开或死循环；悬空引用不能静默丢弃 |
| 编译触发与本次文档获取 | 必做且优先验证 | 独立 CLI 或手工快照不能满足每次编译自动更新 |
| 生成失败隔离、超时、明确警告 | 必做 | 文档辅助流程不能改变业务编译结果，也不能无限等待 |
| 暂存校验后整份替换、保留上次成功结果 | 必做 | 避免半成品、旧接口残留，以及生成失败破坏已有 Skill |
| 最小来源与生成状态 | 必做 | 区分最新成功生成、更新失败沿用旧版、尚无有效产物 |
| 路径、资源上限与指令隔离 | 必做但保持简单 | 安全写入约定目录；来源描述只能作为资料，不能变成受信指令 |
| 核心测试与测试案例 Maven 构建验证 | 必做 | 证明契约保留、完整生成、重复执行和失败隔离；不要求真实 web 环境 |
| 前端使用效果 | 用户人工校验 | 从实施计划移除，等待用户自行反馈，不作为交付阻塞项 |
| 唯一完整汇总 Skill 与单服务 Skill 共存 | 必做 | 输出模式、明确服务清单和独立安全发布，不做 OpenAPI 语义合并 |

## 3. 哪些当前没有必要做

| 原设计内容 | 当前处理 | 原因 |
| --- | --- | --- |
| 只读下载服务、HTTP API、仓库索引、网关、缓存头 | 暂不做 | 属于分发和部署体系，不是生成 Skill 所必需 |
| 强制 ZIP、独立 `skill verify`、压缩包防篡改体系 | 暂不做 | 直接生成可使用的 Skill 目录即可；保留生成前后的必要结构校验 |
| `skillPackageId`、identity envelope、全量文件摘要、不可变版本发布 | 暂不做 | 当前无包仓库和版本下载需求；来源摘要与生成状态足够追踪 |
| ZIP 字节级可复现、压缩参数与跨主机一致性门禁 | 暂不做 | 文件命名和内容排序稳定即可，不以发布制品体系作为交付前提 |
| 独立 CLI 和 `smartdoc.yaml` 配置体系 | 暂不做 | 优先一个编译集成入口和最少构建参数，避免两套入口 |
| 自动分发到其他项目、安装器、锁文件、漂移管理 | 暂不做 | 本次自动更新指生成端产物更新；不推导为跨仓库同步需求 |
| 完整微服务测试平台（数据库、注册中心、网关、自建 UI） | 暂不做 | 首个真实样例采用多包、多文档分组的最小 Spring Boot 服务；按用户要求提供 Swagger UI 浏览接口 |
| 搜索、BM25、向量、RAG、AI enrichment、聊天 UI | 暂不做 | 前端通过已有 Agent 读取 Skill，无需再造知识平台 |
| TypeScript 生成、额外知识源、多 Agent 格式、MCP | 暂不做 | 不服务当前唯一目标 |
| Swagger 2.0、其他 OpenAPI 版本、YAML、外部引用兼容 | 暂不做 | 保持当前输入边界，避免扩大兼容矩阵 |
| 通用 URL 采集平台、自动启动业务服务 | 暂不做 | 最新文档由目标项目已有生产流程接入；当前不建设采集平台 |
| 跨服务统一版本发布、跨仓库调度 | 暂不做 | 完整汇总 Skill 已纳入生成范围，但不引入全局发布和调度平台 |

不因这些能力将来可能有用而预留模块或排入当前路线图。

## 4. 编译更新流程

```text
目标项目 Maven 构建流程
  → SpringDoc / NextDoc4j 产出本次 OpenAPI JSON
  → OpenAPI 读取与校验
  → Skill 暂存目录生成
  → 内容、引用和路径检查
  → 整份替换正式 Skill 目录
  → 记录本次更新成功

任一 Skill 更新步骤失败或超时
  → 放弃本次半成品，保留上次成功 Skill（如果存在）
  → 记录 WARN 和更新失败状态
  → 业务编译继续，由业务编译自身决定成败
```

### 4.1 每次编译的触发语义

- 在已配置集成的目标项目中，每次执行约定的 Maven 构建命令都触发一次更新，不要求独立 IDE 编译入口。
- 无源码变化的再次构建也必须覆盖；具体 phase 由目标项目按文档生产者的实际执行阶段配置。
- 生成逻辑不能因为编译器判断“无源码变化”而被跳过。
- 不能把 `verify` 路径声称为普通 `compile`；验收以目标项目约定的 Maven 命令为准。
- Java 17 / Maven 是现有基础，薄 Maven 插件已验证静态文档的 `compile` 接入；运行时 springdoc 因依赖已编译应用，在样例中采用独立的 `verify` 入口。
- 如果文档生产依赖本次 class 文件，必须验证执行顺序满足该前置条件。
- IDE 仅在委托同一 Maven 命令时进入支持范围；IDE 自有编译器不在当前范围。

### 4.2 本次接口文档的新鲜度

核心转换器逐份读取固定下来的 JSON，一个服务的一次更新接收完整的配置文档集合；生产输入不能长期停留在手工提交的测试快照。

- 文档准备与 Skill 转换必须属于同一次更新流程，并有明确的先后关系与完成结果。
- 本次文档准备失败时，即使磁盘还有上次 JSON，也必须标记更新失败；不得读取旧文件后声称 Skill 已跟随本次代码更新。
- 输入就绪后固定其字节，避免读取过程中变化；源摘要用于追踪所用内容，不证明文档与代码同步。
- 契约未变化时摘要可保持相同，这仍是一次成功更新。
- 生产输入只接受 SpringDoc / NextDoc4j 的 JSON 产物，并必须接入同一个 Maven 构建流程；手写静态契约只保留为测试输入。
- 对本次构建生成的文档，可要求每份文件的修改时间不早于 Maven 会话开始，并在读取前后保持大小和修改时间稳定；内容未变化仍可视为本次成功重写。
- 当前仓库已验证 SpringDoc 运行时样例。NextDoc4j 以 SpringDoc/OpenAPI 3 为引擎，SmartDoc 只读取目标项目为它显式导出的 JSON，不依赖 NextDoc4j UI 或内部 API。
- 不默认启动业务应用、访问已部署旧实例或扫描源码来绕过该问题。若现有文档生产方式不能覆盖编译入口，需先确定最小接入方案。

### 4.3 失败不阻断编译

- 配置错误、文档缺失/过期、解析错误、不支持版本、引用异常、渲染异常、文件权限/替换错误和生成超时，都属于 Skill 更新失败。
- core 返回失败结果或异常；编译集成层统一隔离，输出简明 `WARN`，不把 Skill 更新失败转成业务编译失败。
- Skill 配置解析和文档准备也应在隔离范围内，不能只捕获最后的渲染错误。
- 耗时步骤应有边界；超时须停止该次写入，不能让已超时任务稍后覆盖产物。
- 不吞掉原本的 Java 编译错误、测试错误或其他构建失败，也不将整个 Maven 命令强制改成成功。
- 首次生成失败时没有有效 Skill，应明确说明；已有旧版时说明“本次更新失败，保留上次成功结果”。
- JVM/进程终止、Maven 自身无法启动或插件无法加载等情况，不能靠尚未运行的生成器捕获；这是实现边界，不能承诺掩盖宿主构建故障。
- 样例中的 springdoc HTTP 抓取失败可继续到 SmartDoc 并由其隔离；Spring Boot `start` 失败发生在 SmartDoc 之前，仍会中止 Maven。生产方案必须明确是否接受这一边界。

### 4.4 安全更新

- 输出目录只容纳该生成器拥有的 Skill 文件，禁止把源码根目录或混有人工内容的目录作为替换目标。
- 每次在独立暂存区生成完整结果，通过检查后再替换正式结果；不先清空旧目录。
- 接口删除或重命名后，成功替换应同步清理旧引用文件。
- 替换失败时恢复或保留旧完整结果；不把非原子的文件逐个覆盖声称为原子更新。
- 同一输出路径禁止并发交错写入，采用最小写入互斥；发生冲突时该次更新失败并警告，不阻断业务编译。
- 更新状态存放在 Skill 目录之外，失败时不修改旧 Skill 内的来源记录；状态文件无法写入时至少输出警告。

### 4.5 服务与多文档的协调规则

- 显式配置稳定且在消费项目内唯一的 `serviceId` / `skillName`，以及服务内唯一的 `documentId` 和各文档来源。每份文档仍须符合 OpenAPI 3.1.0 JSON 输入契约。
- “文档”是目标 POM 指定目录中发现或显式列出的 OpenAPI JSON 文件/分组，不是额外的接口、Schema 或文字说明清单。JSON 中存在什么就转换什么，缺失的接口事实不补造。
- 目录扫描模式以本次发现的 JSON 作为完整输入集合；没有 JSON 时跳过生成。需要固定分组集合的项目可以改用显式文档配置，此时任一配置文件未产出都会放弃该服务本次更新并告警。
- 一份文档失败则该服务本次更新失败，保留该服务旧完整 Skill；其他服务继续更新，业务编译结果不受 Skill 失败影响。没有旧结果时明确报告无有效 Skill。
- 从配置中显式移除文档分组后，下一次成功更新清理该组旧文件；缺失必需输入不能当成用户删除了分组。
- 每个服务指定一个生成责任入口；多个包不重复触发，多模块不能通过插件继承让每个子模块都写同一 Skill。普通完整编译中每个参与的服务生成一次。
- 全量、单服务和并行构建通过仓库案例验证。汇总必须由显式协调入口执行；入口收到不完整必需输入时失败并保留旧汇总。未执行协调入口的局部构建不会更新汇总；真实目标环境接入不再是验收任务。
- 无关服务不因局部编译被重新生成、删除或要求上线。文档生产可依赖本服务编译所需模块，但不得额外要求所有微服务同时运行。
- 输出目录、暂存区、互斥和更新状态均按服务隔离。两个服务映射到同一输出位置时报告配置冲突，不互相覆盖；不得清空所有服务共用的输出父目录。
- 协调模块通过显式 Maven 依赖保证位于服务模块之后，仓库案例覆盖并行执行；不能假定父 POM 先执行就意味着子模块文档已就绪。

### 4.7 微服务汇总与共存

- 旧版顶层 `serviceId` / `skillName` / 文档配置保持兼容，默认 `outputMode=service`。多服务使用 `services` 列表，每项包含身份和目录或显式文档；不能混用顶层单服务参数。
- `service` 仅更新独立服务；`aggregate` 仅更新完整汇总；`both` 更新独立服务后生成汇总。汇总必须配置独立的 `aggregateId` 和 `aggregateSkillName`，服务身份、目录名及汇总身份不能冲突。
- 清单中的每个服务都是必需成员。与旧单服务空目录 SKIPPED 不同，成员目录为空、文件缺失、过期或无效都使该成员及汇总失败，不能发布缺少服务的“完整”产物。
- `both` 使用本次各服务成功更新时生成的完整内存结果，不重读上次生成的 Skill，也不以旧服务替代失败成员。成员失败不阻断其他独立服务；汇总输出失败不撤销已成功的独立输出。整套目录不是跨服务事务。
- `aggregate` 在一个有超时的任务内读取所有成员、转换和组装，仅发布汇总。`both` 中每个服务任务和最终汇总组装分别受 `timeoutSeconds` 限制。超时任务不能在之后发布输出。
- 汇总是一份可独立复制的完整 Skill，只有一个 `SKILL.md`，根目录索引先选服务，再进入各服务的文档目录。全部引用按 `references/services/<serviceId>/references/` 保存，不依赖外部安装的单服务 Skill，不合并 OpenAPI 或猜测网关地址。
- 汇总 `source.json` 使用 `kind=aggregate`、成员来源列表和带 serviceId 的文档列表；其顶层 serviceId 使用 aggregateId 作为发布所有者。状态、锁、暂存和备份复用既有安全发布边界并独立于各服务。
- 配置最多 32 个服务；汇总准备结果及最终输出受 10000 文件/64 MiB 总量限制，每份文档仍遵守原输入限制。清单内同名接口、Schema、认证定义保持服务和文档隔离。
- 成功移除成员后，汇总中的旧引用随整份替换清理。切换模式或移除成员不会自动删除独立目录，避免影响其他使用者。
- 唯一协调入口放在全部文档生产之后；`both` 负责独立输出时不得另设重复写同一目录的服务入口。跨仓库输入由调用者先准备为本地 JSON，不增加采集、安装或调度服务。

### 4.6 多文档的内容隔离

- operation 使用 `serviceId + documentId + method + path` 作为归属键；Schema、安全定义和本地引用以文档为解析边界，保留原始 JSON Pointer。
- 两份文档都有 `User`、`bearerAuth` 或 `GET /users` 时分别保留，目录标注分组和来源，不按名字覆盖或猜测它们相同。
- `$ref` 只解析当前文档的本地目标，不因为其他文档恰好有同名 Schema 就跨文档匹配。外部引用仍不支持。
- 不把多份文档直接拼成一份 OpenAPI。分别解析后组织为一个服务 Skill 的目录和引用，避免引入契约合并与自动去重规则。
- 保留各文档适用的 `servers`、路径和鉴权信息；不能猜测网关前缀、服务地址或跨服务调用流程，缺失时标注未知。

## 5. 最小 Skill 内容

默认输出为 `target/generated-resources/smartdoc/<skillName>/`。它属于 Maven 构建产物，`clean` 后不保留。

```text
<skillName>/
├── SKILL.md
└── references/
    ├── catalog.md
    ├── source.json
    └── documents/
        └── <documentId>/
            ├── operations/*.md
            ├── schemas/*.md
            └── tags/*.md      # 需要时生成导航
```

- `SKILL.md`：固定受信模板、名称和用途、如何查找接口与继续读取 Schema；文档自由文本不进入此指令文件。
- catalog：服务、文档分组、method、path、operationId/名称、简短描述和引用路径；可含 tag 导航。单文档也使用稳定 documentId，新增分组不改变已有引用路径。
- operation：参数位置/必填/序列化、请求体及媒体类型、响应状态/响应体/响应头、鉴权、弃用信息和原有示例。
- Schema：类型、字段、必填、枚举、约束、数组、组合、可空、readOnly/writeOnly 和直接引用；正确区分必填与可空。
- 保留参数和鉴权的继承/覆盖语义，以及共享、多级、递归和内联 Schema；未知事实不推断，未支持语义明确提示。
- 生成链接必须可达；文件名稳定、安全并防止大小写冲突；超大内容不能静默截断。
- `source.json` 记录 serviceId、完整 documentId 集合及各文档版本/摘要、生成器版本，不引入包身份体系。最后尝试时间、成功/失败和失败原因记在服务独立的目录外更新状态中。

前端将生成目录放入已有项目 Skill 位置后，通过 Agent 查询接口并辅助编写调用代码。当前不建设下载服务或跨项目自动同步；生成器本身不执行业务接口。

## 6. 最小工程边界

| 单元 | 职责 | 当前状态 |
| --- | --- | --- |
| `smartdoc-agent-core` | 按文档解析 OpenAPI、隔离本地引用、组织服务 Skill、渲染、完整校验与安全发布 | P0/P2/P3 已实现并通过 54 项测试；旧 IR 保持删除 |

## 7. 验收与实施顺序

先写失败测试，再实现对应行为。内容生成器、安全目录更新、Maven 插件和运行时 SpringDoc 样例接入已经完成；目标项目只需显式提供服务映射、JSON 路径、责任模块和执行 phase。

可执行任务、状态和完成证据维护在 [工作计划](codex/TASKS.md)。P0-P4 按测试案例范围完成；P5 前端/web/真实环境验收已由用户移除；P6 是汇总及共存配置。用户人工校验 Skill 后可另行反馈，不是当前未完成门禁。

首个真实样例采用最小 Spring Boot 测试服务：多个 Java 包、显式文档分组、带契约注解的少量接口 → 在测试与集成测试流程中启动服务并导出多份 JSON → 断言精确版本和接口/字段内容 → 固定为 core 输入并验证运行时生成 → 实现该服务的一个 Skill。静态文档的普通编译、多服务隔离，以及运行时文档的 `verify` 顺序和抓取失败均已有独立证据；不能把后者称为普通 `compile` 覆盖。

1. **先验证接入可行性**：确定目标编译入口、当前 OpenAPI 生产方式和输出位置；验证执行先后关系。修复当前缺失 core POM 的构建基础时不隐式恢复用户删除的旧 IR。
2. **完成最小内容转换**：用一份脱敏 OpenAPI 3.1.0 文档及少量边界样例，覆盖接口、字段、鉴权、共享/递归引用和目录路由。
3. **接入编译与完整更新**：首次编译生成、连续编译再次执行、接口修改反映到 Skill、删除接口清理旧文件、内容不变也执行更新流程。
4. **验证失败隔离**：文档生产失败且旧 JSON 仍在、无效 JSON、悬空引用、无写权限、替换失败、超时和写入冲突；业务代码有效时编译仍成功，旧 Skill 完整且日志明确。业务编译错误仍导致构建失败。
5. **汇总及共存验证**：自动检查独立输出、汇总完整性、同名契约隔离、模式选择、失败保留、删除成员清理及 Maven 配置绑定。

core 日常测试使用固定输入，不启动业务服务、不访问外部引用或调用 LLM。编译集成测试单独验证完整更新流程；不以“单元测试通过”代替“每次编译更新且异常不阻断”的验证。

必需的多服务/多文档验收：

- 单服务多包的一份文档覆盖全部预期接口；包扫描配置错误能通过预期接口检查暴露。
- 同服务两份文档含同名 Schema、安全定义和相同路径时，引用与鉴权均保持各自归属。
- 两个服务并行生成各自 Skill，任一服务失败不妨碍另一个更新；输出冲突不破坏已有结果。
- 同服务一份文档失败时整份 Skill 不更新；分组删除成功后没有旧文件残留。
- 多模块完整编译只生成一次；单服务编译、局部模块编译、无变化重编译和并行编译均有明确触发/未就绪结果。
- 汇总可独立发布且只有一个入口，服务/文档引用全部可达；同名契约保持独立，任一必需服务失败时不发布残缺汇总。

## 8. 已确认的接入契约

- 生产 OpenAPI JSON 只来自 SpringDoc / NextDoc4j；其他生产方式不纳入支持范围。
- 使用 Maven 命令构建。SmartDoc 在生产者完成后执行；SpringDoc 运行时导出对应 `verify`，其他场景由目标 POM 显式选择经过验证的 phase。
- Skill 默认写入 `target/generated-resources/smartdoc/<skillName>/`，不要求跨 `clean` 保留。
- 服务、Java 包、Maven 模块和文档分组由目标项目显式配置，不能自动猜测；每个服务只有一个生成责任入口。
- “文档”只指目标项目列出的 OpenAPI JSON 文件/分组。单一 `openapi.json` 就是一份文档；分组导出的多个 JSON 是多份文档。JSON 中没有的接口或字段不生成，也不需要另列所谓必需业务文档。

这些是当前链路的接入参数，不扩展为下载、安装或运维产品。分发可见性、对象存储、服务部署和包仓库不再是当前工作的阻塞项。
